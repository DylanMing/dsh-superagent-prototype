# 002 授权

> [English](002-authorization.md) | 中文

授权决定谁可以发起工作，以及这项工作可以包含什么。本文档建立在 [001 领域模型](001-domain.zh.md) 之上。

宿主负责强制执行允许名单、规则和授权。消息、评论和被引用的文档都只是做决定的输入；它们无法改变这些权限。

## 触发的两条路径

### 评估：决定是否开始工作

来源会记录一条消息是否指向智能体：`mention` 表示提到了机器人或智能体账号，`direct` 表示私信。准入会检查发送者和该来源的策略：

- 允许名单上的人如果指向智能体，就构成一个明确请求。
- 人在已有任务的对话线程上的后续发言，遵循下面的规则。
- 其他人类消息按它们所属的接收范围使用准入表。
- 来源机器人名单上的机器人可以产生推断候选，但永远不能产生明确请求。其他机器人不予准入。

### 订阅：延续已有的工作

已订阅对话线程上的每条消息，都会作为上下文到达订阅它的任务，包括来自机器人和 CI 的消息。这种投递绕过准入，也不授予任何新的授权。每个任务仍受其授权的限制。

人在某个任务自己的对话线程上发的消息，归该任务的执行器判断。主会话把消息附加到任务上时也是如此。只要消息由执行器拥有，它就不经过评估，也不会得到决定。每个执行器要么在任务范围内处理该请求，要么把它交回，以便路由到别处。

只要任务存活，归属关系就持续存在，即使有人移除了它的订阅。对于已结束、但并非被人停止、且有消息正等待恢复它的任务，归属关系同样存在。

主会话会收到一条后续通知。当消息归执行器所有时，主会话只能按人的要求停止工作；接受、附加、忽略和重新排队都会被拒绝。停止仍然要经过准入，使用下文描述的后续强度。

### 交回与释放后续发言

当消息请求的工作超出任务范围，或属于另一个任务时，执行器会把它交回一次。任务保留它的订阅。如果附加的对话线程并不相关，执行器会把在那里它拥有的消息交回。

只有当没有任何任务再拥有这条消息时，它才会进入一次新的评估。它的候选会带上执行器给出的理由。准入把它当作该对话线程上的一条普通消息来判断，主会话可以接受它、把它附加到别处，或忽略它。交回一条任务本就不拥有的消息（例如机器人消息，或人已经发去评估的消息）不会排入任何队列。

任务结束时，会释放其执行器没有读到、也没有接手处理的后续发言。这包括从未投递给执行器的消息，以及在其最后一次报告或回合结束之后投递的消息，前提是执行器既没有确认回复、也没有回答、也没有交回。每条被释放的消息，在没有任何其他任务拥有它时进入评估。停止只结束被停止的那个任务的工作。

被停止的任务不会把它的停止消息再次送进评估，除非另一个任务把它交回。停止它的主会话可以把这条消息的其余部分当作新工作接受。

人可以从面板把一条被拥有的后续发言送去评估。如果主会话随后又把它附加回某个存活的任务，执行器会再次收到它。当没有任何有效的判断覆盖这条消息时，面板也会提供重新评估。

### 仅作为上下文的订阅

执行器可以关注一个相关的对话线程，例如另一个 Issue 或拉取请求，以获取上下文。那里的消息会到达任务，但不授予任何授权，也不带来后续强度。那里的人类消息不会恢复已结束的任务，除非主会话附加了来自该对话线程的消息。主会话关于其他工作的备注同样只是上下文。

没有到达任何任务的人类消息，包括任务已被人停止的那些对话线程上的消息，走评估路径。机器人消息走这条路径，与它们是否投递给已订阅的任务无关。

## 强度

| 强度 | 情形 |
| --- | --- |
| explicit | 名单上的人指向智能体，或在已有任务的对话线程上后续发言；准入表中设为 explicit request 的单元格 |
| inferred | 不在名单上的人在已有任务的对话线程上后续发言，除非其准入单元格为 explicit；准入表中设为 inferred candidate 的单元格；来源机器人名单上的机器人发的、指向智能体或到达来源接收全部消息之处的消息 |
| not admitted | 其他任何机器人的消息、准入表忽略的一切，以及接受模式为 `off` 时所有推断的情形 |

对于不在名单上的人，显式的准入单元格优先，即使是在已有任务的对话线程上也是如此，并且在任何接受模式下都有效。否则他们的后续发言属于推断，在 `off` 模式下不予准入。仅在上下文中被关注的对话线程上的消息，使用准入表而不是后续强度。

## 准入

每个来源的策略都有一张准入表。它的行是接收范围：

- **飞书 Feishu：**每个已配置的群、机器人能从其中收到提及的其他群，以及私信。只有在飞书卡片上把 **其他群** 设为 **仅 @** 时，其他群才会被接收。
- **GitHub：**新的 Issue、新的拉取请求、评论，以及默认分支的 CI。

一行最多有三个单元格。每个单元格决定一条消息是变成明确请求、推断候选，还是什么都不变：

| 单元格 | 可选值 | 默认 |
| --- | --- | --- |
| 在名单上，未指向智能体 | inferred, ignore | inferred |
| 不在名单上，指向智能体 | explicit, inferred, ignore | ignore |
| 不在名单上，未指向智能体 | inferred, ignore | ignore |

未指向消息的单元格，只在来源接收全部消息的地方可用，例如设为 **全部消息** 的飞书群，或打开了接收全部开关的 GitHub 范围。CI 结果没有发送者，因此它的行只提供最后一个单元格。机器人消息使用机器人名单，而不是这些单元格。

把“不在名单上、指向智能体”这个单元格设为 explicit，可以让该范围内的任何人通过提及智能体来请求工作。这对专门的支持群可能很有用。推断候选仍然取决于接受模式。后续发言通常绕过这张表，但显式单元格仍然会赋予明确强度。

准入表是策略版本的一部分。削弱某个单元格，不会立即停止在它之下被接受的、仍处于 open 状态的任务。当这些任务在恢复前重新校验时，它可能会撤销它们的授权。

### 机器人与自动评审者

宿主把 GitHub Apps、以 `[bot]` 结尾的登录名，以及飞书机器人识别为机器人。来源可以列出诸如 `dependabot[bot]` 这样的机器人，它们的消息可以成为推断候选。它们要么必须指向智能体，要么必须发在接收全部消息的范围里。它们不能发起明确请求，也不能停止任务。

使用普通账号的自动评审者，在宿主看来算作人。它的评论会到达已订阅的任务，并产生后续通知。团队提示词文本必须把这类账号标明为自动评审者。

## 候选的路由

主会话用 `orchestrator_route` 路由明确候选。一次调用可以包含多个接受、附加、停止或忽略的决定。每一项都独立处理：某一项被拒绝或缺少某个字段，不会阻止其他项执行。

推断候选通常需要完整的研判。有一个捷径：如果它的卡片明显不涉及任何已启用的规则，例如普通闲聊或无关讨论，主会话可以直接忽略它。决定会记录 `ignoredFromCard`，以区别于基于规则的研判。主会话在其策略提示词段落中读取已启用的规则。

接受推断候选始终需要研判。直接接受会拒绝准入没有认定为 explicit 的触发。

## 接受模式与规则

接受模式是策略的一部分：

| 模式 | 效果 |
| --- | --- |
| `off` | 任何推断都不会成为候选，例如未指向的消息、机器人的消息，或不在名单上的人的后续发言 |
| `observe`（默认） | 推断候选会被研判；正向的研判会记录为一条标记“将接受”（would accept）的忽略，且不会接受任何东西 |
| `auto` | 对推断候选的正向研判会接受它 |

明确请求在任何模式下都有效。从 `observe` 开始，在查看记录下来的决定之后再切换到 `auto`。每次研判会对每条已启用的规则恰好判断一次，无论是否匹配。主动接受至少需要匹配一条规则。

每条规则描述一类主动工作。任务的授权会记录匹配到的规则，其执行器会收到这些规则的名称和指令。

对于该任务，规则中的流程和沟通要求会覆盖默认值。静默规则可以抑制确认回复；评审规则可以指定所需的评审者，以及合并前的批准。适用于每个任务的要求则应放在团队提示词段落里。

## 策略版本

规则、接受模式和每个来源的策略共同构成策略版本。每份授权都会记录它被接受时所依据的版本。

版本变化会丢弃正在运行的评估，并重新排队它们的触发。它还会向每个受影响的存活任务发送一条“策略已变更”的输入。该输入会说明是否：

- 某条匹配到的规则发生了变化（包括它的新文本），或不再适用；
- 请求者不再可以发起工作；或
- 主动工作不再被接受，例如因为模式从 `auto` 改变了。

不受影响的任务不会收到通知。这项变更不会立即撤销存活任务的授权。

来源配置与策略是分开的。它控制什么能进入系统：读取哪些群，以及某个范围是接收全部消息还是只接收提及。授权会记录它的来源和接收范围。恢复要求来源仍在监听该对话线程，但不要求它在那里仍能接收全部消息。

回复在来源关闭期间会等待。如果来源不再监听它们的目标，它们会被丢弃。

关于执行器可以用自己的结果做什么的条件，例如它何时可以合并，并不决定谁可以授权工作。它属于智能体的指令，不属于策略。

## 恢复与停止

已结束的任务保留它的授权。人在它自己的某个对话线程上发的消息，可以恢复同一项工作，无需新的评估或决定，也不论发送者是谁。机器人和 CI 不会唤醒已结束的任务。执行器会判断该请求是否落在范围内；如果不落在范围内，就结束这一轮。

只有三种操作会改变授权：接受创建它，人的停止撤回它，重新校验失败撤销它。被某人停止的任务保持已结束状态，不再接收任何东西。在那里请求的工作需要新的接受。

### 恢复前的重新校验

来源必须仍在监听最初的对话线程。其余检查取决于授权的依据：

- 由明确后续发言产生的授权直接通过校验。
- 由推断产生的授权需要 `auto` 模式，且其匹配到的规则仍然启用。
- 由某个表单元格准入的授权，在今天的表和发送者成员关系下，仍必须至少获得与原来相同的强度。因此，把某个发送者从名单上移除，可能会撤销通过“名单内发送者”单元格接受的授权。
- 机器人产生的授权要求该机器人仍在来源的机器人名单上。由推断产生的表授权和机器人授权还需要 `auto` 模式，以及匹配到的规则处于启用状态。
- 其他授权要求发送者仍在来源的允许名单上。

如果重新校验失败，任务保持已结束状态，不接收任何等待中的消息。每条消息都被视为没有到达任何任务；如果没有其他任务拥有它，它就进入评估。主会话不会被告知它到达了某个 worker。在处理暂停之后同样适用。附加到该任务会被拒绝，进一步的工作需要新的接受。

- **人在对话线程里说“停止”只是一个普通触发，** 由评估来决定是否停止。执行器不能宣称某人要求它停止。
- **在面板里点停止是一条命令。** 它直接作用于任务，并被记录为手动停止。
- **等待条件属于来源。** 诸如“N 小时没有指派人”这样的条件，本身就是一个会自己等待并再次检查的来源；评估永不等待。

## 当评估没有完成时

时限从候选到达主会话时开始计算。等待投递所花的时间不计入，未被投递的候选也永不过期。

超时的评估会把它的触发排队，等待另一次尝试。连续两次重试之后，第三次超时会记录 `unavailable`。研判失败也会记录 `unavailable`；之后的触发可以启动新的评估。策略变更，或依据过时策略做出的决定，会记录 `unavailable`，并立即按当前版本重新排队该批次。

`evals` 健康条目会报告最近一小时内未解决的 unavailable 决定。`scripts/dsh-superagent status` 会包含这个错误。

只有当 unavailable 决定距今不到 24 小时、仍是其对话线程上最新的决定、尚未被忽略、且该对话线程既没有排队也没有在评估时，面板才会请求人工关注。人可以再次评估该触发，或忽略这个问题。
