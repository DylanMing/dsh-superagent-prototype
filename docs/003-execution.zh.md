# 003 执行

> [English](003-execution.md) | 中文

本文档讲述一个已被接受的任务（Ticket）如何经历执行、交付与恢复。它建立在 [001 领域模型](001-domain.zh.md) 与 [002 授权](002-authorization.zh.md) 的基础之上。

## 任务阶段

每个未结束的任务都处于一个阶段，由它在等待什么决定。自上而下读表，第一行匹配者生效。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| person / delivery | 把一条输入投递给执行器会话失败；它在 2 秒后重试，之后每次延迟翻倍、最多到一分钟，投递成功、出现新的派发或任务结束都会清除它 | Input undelivered（输入未送达） |
| person / answer | 它有一个待关注项（Attention） | Awaiting answer（等待回答） |
| person / review | 最新报告为 `ready` | Awaiting review（等待评审） |
| person / blocked, failed | 最新报告为 `blocked` 或 `failed`，且此后没有人的消息到达该任务 | Blocked · Failed（受阻 · 失败） |
| working / queued | 没有派发，或有一个待处理的派发 | Queued（排队中） |
| idle | 最新报告为 `waiting`，或派发已结束 | Waiting for a Trigger（等待触发） |
| working | 其余所有情况 | Working（工作中） |

一个 `person` 阶段意味着任务缺少人的输入就无法继续。新的来自人的消息会把 `blocked` 或 `failed` 的任务释放给它的执行器，于是它转入下一个匹配的阶段，通常是 `working`。

`idle` 的任务已在没有悬而未决问题的情况下结束本轮。订阅的对话线程（Thread）上出现触发（Trigger）可以继续它。

## 执行器

每个任务都会得到一个名为 `worker-<ticket id>` 的执行器会话（Session），以及一个以任务短名命名的目录。目录创建在配置的执行根目录下，默认是 `<stateDir>/work`。

执行器会话以操作系统的当前用户身份、无需审批地运行命令。它们的 `dsh-superagent-worker` 预设包含工作所需的工具，并在 5 秒后把前台 shell 命令转为后台作业。这让 worker（执行器）能在下一步接收新消息，而不用等待长命令结束。

主会话使用 `dsh-superagent-router`，具有同样的 5 秒 shell 与等待作业上限，以及为路由而精简的工具集。会话会保留创建时选定的预设。worker 的子代理使用 DeepSeek Harness 的 `standard` 预设。

### 后台工作与 worker 槽位

当一轮结束时仍有 shell 作业或子代理在运行，任务会保留它的 worker 槽位并保持在工作状态。它不会被报告为等待，主会话也收不到等待报告。作业或子代理完成后，会在同一槽位中带着结果唤醒执行器。一旦一轮结束时不再有后台工作，执行器就会正常上报等待。

每一轮结束后，后台工作最多有 30 分钟完成。到达该上限时，shell 作业会被终止，任务被上报为等待。报告包含执行器最后说的话，以及哪些作业被终止、哪些子代理仍在运行。子代理允许继续。执行器在下一轮读取被终止作业的结果。

把工作交回给人（handoff）会立即释放槽位，并让该报告继续有效。这适用于 `ready` 报告或提出问题之后（除非此后又有输入到达），也适用于任何 `blocked` 或 `failed` 报告之后。

交接时，子代理会停止。shell 作业——例如为评审而启动的服务器——可以继续运行，直到派发结束。它们不占用槽位，也不受 30 分钟上限约束，即使在后续轮次之后也是如此。它们的完成不会唤醒执行器；执行器在下一轮读取结果。

人也可以直接在执行器会话中书写来开启一轮。其后台工作遵循同样的规则。

派发结束时，它的 shell 作业会被终止，且不会唤醒会话。它的子代理被释放，它们唤醒的完成轮次会被丢弃。替代它的派发及其等待中的输入会在该关闭过程完成后开始。

在 DeepSeek Harness 进程内停止或重启插件时，走同一条关闭路径。尚未进入会话历史的输入会被保留。关闭时最多等待每个 worker 的后台工作 10 秒；进程重启则会直接终结这些工作。忙碌中被中断的派发会带着恢复说明重新开始。

worker 的子代理（包括嵌套的）使用 DeepSeek Harness 的 `standard` 预设，并具有该 worker 的权限。它们只保留 worker 被允许的工作工具，并在任务结束时失去这些工具。在 `standard` 下，shell 命令在 60 秒后转入后台。子代理结束时，它的作业会被终止。

### 准备任务目录

在第一次派发之前，如果任务目录不存在，准备命令会在执行根目录下用 `sh` 运行一次。它有十分钟时间完成。没有准备命令时，worker 在一个空目录中启动。

命令失败会使任务失败，并记录其输出。重试，或人在任务的某个对话线程上留言，会再次尝试准备。典型命令用 `git worktree` 创建检出。当拉取请求分支路径的最后一段与任务的短名一致时，该拉取请求属于这个任务。

### 并发

任务从一次启动开始（包括准备阶段）或从唤醒其空闲执行器的那次投递开始占用一个 worker 槽位。它在整个活跃轮次中也一直占用该槽位。

配置的并发上限作用于这些槽位，另外为人发来的消息或状态请求保留一个额外槽位。当正常槽位已满时，这类唤醒可以使用额外槽位；而在启动新工作之前，它会先占用下一个空闲槽位。因此新工作无法阻止人继续推进一个已有任务。

其他输入，例如 CI 结果，要等待正常槽位。启动会在 `working / queued` 中等待直到有槽位空出。启动之间并发进行，因此一个慢的准备命令只会拖延它自己的任务。

### 执行变量

准备命令和执行器指令收到相同的执行变量。命令读取环境变量；执行器在其提示词中读取这些变量的值与说明。其中都不包含凭据。

| 变量 | 注册方 | 值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`, `DSH_SUPERAGENT_NAME`, `DSH_SUPERAGENT_TICKET` | 执行器 | 任务的目录、短名和 id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 执行器 | 执行器不得运行哪些命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | 来源所监视的仓库，`owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`, `DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | 代理账号及其提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`, `DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 启动该任务的 Issue 或拉取请求；当它是拉取请求时，还包括其 head ref |
| `DSH_SUPERAGENT_FEISHU_BOT`, `DSH_SUPERAGENT_FEISHU_CHAT` | Feishu | 机器人，以及启动该任务的对话（chat） |

任务特定的值来自它的目录和发起它的触发。其他值来自当前部署设置。只有面板能更改执行环境设置；发送给主会话的文本无法更改配置好的 shell 命令。

worker 通过代理账号的 `gh` 访问 GitHub，通过机器人的 `lark-cli` 访问 Feishu。被禁用的命令在按名称调用时会失败。

这些包装脚本和目录只是建立默认值，并非安全边界。worker 仍然可以通过绝对路径执行程序。

## 合并

自动合并由 **交付要求**（Delivery requirements）提示词决定。宿主没有针对合并的专门决策逻辑。

默认情况下，执行器绝不会以代理账号身份启用自动合并：GitHub 会把合并归于启用者。交付要求中必须指明另一个账号的 CLI 用于合并。若没有指明，则由人来合并拉取请求。

默认指令只对为该任务打开的拉取请求允许自动合并：该拉取请求已就绪、所需审批覆盖了 head 提交，且新增加删除的总行数少于 200 行。在推送新的修订之前，执行器会撤回自动合并。

不带正文的评审（例如批准）也会作为触发到达，并能唤醒等待评审的执行器。这些指令约束的是代理，而不是 GitHub 的合并规则。若要对审批做强制，就在分支保护中要求审批并清除过期审批。省略合并 CLI，或删掉自动合并那一段，即可要求手动合并。

## 任务如何结束

- **没有拉取请求的就绪：** 一份 `ready` 报告会以已完成状态结束该任务。
- **无事可做：** 执行器若发现没有需要人去处理的工作——例如请求无法复现或已被取代——就上报 `dropped`。任务会在不发送消息的情况下结束，除非有匹配的规则要求发送消息；人此后在其对话线程上的消息会让它恢复。

### 拉取请求

一旦执行器上报了它的起始拉取请求，任务就开始跟踪该拉取请求。它也会跟踪从它的分支打开的每个拉取请求：一旦执行器上报，或被 GitHub 来源发现。重新打开的拉取请求会再次被跟踪。

当它打开的拉取请求都不再处于打开状态时，任务即告完成。如果它没有打开任何拉取请求，那么它跟踪的所有拉取请求都必须已关闭。随后它以最后一次相关关闭的结果结束，并保留其订阅（Subscription），使之后的人工评论能够恢复它。

当恢复的、重试的或恢复执行的工作尚未完成时，关闭拉取请求不会结束任务。若执行器确认或答复了它负责的后续消息，但此后尚未给出非进度报告，也没有在读到该消息后结束一轮，关闭同样会等待。一旦满足同一套拉取请求完成规则，之后的一份 `ready` 报告就会结束任务。

聊天频道（Chat Channel）会收到一条关于拉取请求结果的最终通知。GitHub 本身已在拉取请求上展示结果。移除任务对某个拉取请求的订阅，也会停止跟踪该拉取请求。

因此，“等待评审”（Awaiting review）意味着有一份带拉取请求的 `ready` 报告。

### 后续消息与上下文对话线程

执行器在其任务自己的对话线程上裁决人的后续消息。它处理范围内的请求，并把超出范围或属于另一个任务的请求交回。一旦没有执行器拥有该消息，它就成为主会话的候选。除此之外，主会话只可在人要求停止工作时才对后续消息采取行动。

当会话把一条输入纳入某个步骤，并且随后给出报告或结束一轮之后，该输入才算已读。任务结束时，未被确认（acknowledgement）、未被答复或未被交回的未读消息会回到评估（Eval），如 [002 授权](002-authorization.zh.md) 所述。已读但未处理的、例如道谢的消息则不会。

仅为上下文而跟踪的对话线程仍会投递消息，但不会让任务拥有人工后续消息的所有权，也不会恢复已结束的任务。那些消息可以被独立评估。

来源在仍有活跃任务订阅期间轮询已订阅的对话线程，并在最后一次触发与订阅任务结束两者中较晚者之后继续轮询两周。此后，消息只通过常规入口到达：GitHub 通知或 Feishu 实时事件。

## 失败与恢复

### 执行器受阻或失败

当执行器会话报告 `blocked` 或 `failed`，或启动失败、发生错误（记录为 `failed`）时，任务不再接收任何自动输入。

模型提供方或网络的暂时性失败——HTTP 408、429 或 5xx，以及被拒绝、被重置或超时的连接——会先重试，共三次且退避递增：启动会再次运行，轮次失败的 worker 会被要求继续；失败的准备命令不会重试。

一旦失败，CI 与机器人消息仍会记录在它上面，但不会被投递，也不会唤醒会话。

它的工具仍然可用，所以人可以直接在该会话中继续。

失败的启动不会自行重试。

人的消息、此后一份既非 `blocked` 也非 `failed` 的报告，或一次重试，都会结束这种挂起。

该状态由已存储的报告和输入推导得出，因此重启后仍会保留。

### 重试

当一个未结束的任务处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用：新的派发会重新启动其 worker 并接管等待中的输入，对以上每种情况都是解法。

一旦人的消息到达了受阻或失败的任务，执行器就持有该消息，因此任务显示为工作中，或在失败的启动重新开始时显示为排队中，并且不提供重试——除非投递该消息本身失败了。

重试会结束当前派发，并在同一个执行器会话、目录、分支和拉取请求中启动新的派发。

执行器模型只在创建会话时生效；已有会话保留其模型。

### 重启

正在运行的派发会以 "host restarted" 结束，新的派发会带着恢复说明开始，要求执行器在重复任何外部动作之前检查其目录、git 历史和 GitHub；按任务从旧到新的顺序处理。

处于等待、就绪、受阻或失败状态的派发保持不变，除非在该报告之后有输入到达它们，这种情况下它们也会重新开始。

会话、目录、订阅、待发消息以及下文所述的已存储工作都能在重启后保留；每个执行器会话把哪些消息纳入其历史的记录也能保留，这是某个步骤在认领这些消息之后、调用模型之前所做的：被重启切断的某个轮次已纳入的消息，一旦随后出现报告或一轮结束就算已读；而某个步骤已认领、却在进入历史之前被取消或错误切断的消息，算作未读。

重试或重启会把投递给它所替代的那个派发、但执行器会话未纳入的消息重新交给新的派发，取消或被切断的步骤可能丢掉了它们；若会话中仍有一份在等待的副本（由重启保留或跨崩溃持久化），它会在新派发的第一条消息之前被取出，因此新的投递是唯一的副本。

### 已存储的工作

dsh-superagent 在做出决定之后要做的事——例如把候选、后续消息或报告转发给主会话、启动派发、投递输入——都是先存储，后执行。

失败的中转或投递（例如无法触达其会话）会在 2 秒后重试，之后每次延迟翻倍、最多到一分钟；失败的启动则会使它的任务失败，除非该失败是上文所述的暂时性失败。

每一类工作只有在某个条目连续失败三次之后，才会在概览的系统问题中报告错误；失败的输入投递则显示在其任务上。

发往主会话的中转保持顺序，通知也是如此；一个失败的中转会挡住同类的后续条目。

### 来源失败

GitHub 来源会独立读取每个 Issue、拉取请求和对话线程：读取失败会把错误留在其对话线程上，在下次轮询时再次读取，并计入来源的错误；默认情况下连续三次轮询失败后来源才报告错误；任何成功的轮询都会重置计数。

当代理失去对某个私有仓库的访问权限时，GitHub 也会返回 404，因此 404 会被重试。

被通知的 Issue 或拉取请求若读取持续失败，会在首次读取失败一天后被丢弃；若 GitHub 报告其已删除，则立即丢弃。此后它不再导致轮询失败，其对话线程保留该错误，来源状态中会列出它。

它的读取位置保持原样，因此之后的某次通知或对其对话线程的一次轮询会读到失败读取所漏掉的内容。

Feishu 事件消费者会报告每一次失败，而对已订阅话题的轮询会把每次失败留在其对话线程上。

GitHub 列表或 Feishu 页面中格式有误的条目会被跳过，来源状态会计数它。

### 频道失败

外发消息会作为已存储的工作被存储并发送，失败后以退避重试，从 5 秒起、每次翻倍，最多到 300。

一个任务发往同一个对话的消息按入队顺序发出，因此它的确认回复先于它之后的答复或结果：当同一任务发往同一对话的较早消息尚未发出时，后面的消息会等待，直到那条消息连续失败三次并显示为问题。

其他任务的消息，以及不属于任何任务的消息，不会等它。

有失败尝试的消息在发出或被撤回之前，都算一条系统问题。

只有在其来源不再监听该对话，或来源答复该对话永远无法收到消息时，消息才会被丢弃；来源关闭期间，它会等待。

来源会对 GitHub 上已删除的 Issue 或已锁定的对话这样答复，也会对已撤回的消息或 Feishu 上已找不到的消息这样答复。

对已不存在的评审评论的回复，改为发到该拉取请求的对话中。

被丢弃的消息保留记录，包含丢弃的时间和原因以及它所属的任务，因此它永远不会再次入队；一条被丢弃的确认回复会显示为已丢弃，而不是已发送。

### 暂停处理

停止分发、新的评估、评估超时、输入投递和回复；已在进行中的启动会等到处理恢复。

来源仍会继续记录触发，运行中的执行器轮次不会被打断。

人发往已结束任务的消息会等待：暂停后的第一次处理会恢复该任务，前提是它的授权范围（Mandate）在当时的策略（Policy）下仍然成立。

进行中的评估在暂停期间不会过期；它的截止时间按暂停时长顺延。

### 无效配置

已存储的来源配置若被其类型拒绝，会禁用该来源实例。
